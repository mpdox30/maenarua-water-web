## 2. ส่วนที่ 1: สาเหตุและการแก้ไขโมเดล Horizon 5

### 2.1 สาเหตุที่พบ

ตรวจสอบ `deployment_regressors_no_stage1.pkl` พบว่าโมเดล h5 (CatBoost, depth=2) มีค่า **`random_strength=0.217`** (ต่ำผิดปกติเทียบกับ h4=2.70, h6=1.99) และใช้ต้นไม้ **272/300 ต้น** (`best_iter=271` — เกือบเต็ม iterations ที่กำหนด) ซึ่งเป็นสูตรที่เสี่ยง overfitting สูง — random_strength ต่ำทำให้ไม่มี randomness ช่วยลด variance ระหว่างเทรน และจำนวนต้นไม้ที่มากเกินไปทำให้โมเดลจดจำ (memorize) ค่า delta สุดขั้วบางจุดในชุดเทรนไว้

หลักฐานยืนยัน:
- **`val_nse` (in-sample) = 0.944** แต่ **`test_nse` (single split 57 แถว) = -1.397** — ช่องว่างนี้กว้างกว่า horizon อื่นทั้งหมดมาก ชี้ชัดว่า overfit
- Delta ที่โมเดลทำนายบนชุดเทรนทั้งหมดมี **std = 101,386** (สูงกว่า horizon อื่นมาก) — บ่งชี้ว่าโมเดลไม่เสถียร (unstable) พร้อม "ระเบิด" ค่าทำนายเมื่อเจอ input ที่ใกล้เคียงจุดสุดขั้วบางจุดในชุดเทรน
- เมื่อนำ input จริงช่วง 26 ก.ค. – 16 ส.ค. 2026 (ฤดูฝน) มาทดสอบ พบว่าโมเดล production ทำนายค่าคงที่สูงลิ่ว **~85,000–136,000 m³/day ติดต่อกันเกือบ 3 สัปดาห์** โดยไม่สัมพันธ์กับ horizon ข้างเคียง (h4/h6) หรือค่าจริงเลย (ค่าจริงส่วนใหญ่เป็น 0)

### 2.2 วิธีแก้ (h5_v2)

Retrain เฉพาะโมเดล h5 ด้วย feature/data เดิม (`Training_Values_Nofct_7day_Extended_lagfeat.csv`, 12 features เดิม, delta-regression architecture เดิม) แต่ปรับ:
- `random_strength`: 0.217 → **1.0**
- ใช้ **early stopping** (validation-based) แทนการ fix iterations=300 ตรงๆ — ผลคือโมเดลสุดท้ายใช้ต้นไม้เพียง **64 ต้น** (แทน 272 ต้น)
- Hyperparameter อื่นคงเดิมทั้งหมด (depth=2, learning_rate, l2_leaf_reg, subsample, rsm)

**ทดสอบผ่าน walk-forward CV (5-fold, TimeSeriesSplit)** บนชุดเทรน: mean NSE จาก **-0.943 → +0.009** (ยังไม่ดีมาก แต่พ้นจากช่วงหายนะ)

### 2.3 ผลการทดสอบบนข้อมูลจริงนอกชุดเทรน (สำคัญที่สุด)

สร้าง feature vector ย้อนหลังใหม่จากไฟล์ "บัญชีน้ำ" รายเดือนจริง (`01_data/Reservoirs/inflow/2026/*.xlsx` + ไฟล์ backup รายวัน) แบบ point-in-time (ไม่มี look-ahead) แล้ว validate ว่าตรงกับค่าที่ log ไว้จริงในอดีต (`forecast_accuracy_log.csv`) — **ตรงกัน 100%** (diff < 0.01 หน่วย) ยืนยันว่าการจำลองนี้แม่นยำ

ผลเปรียบเทียบบน 46 วันจริง (2026-07-14 ถึง 2026-09-01, ไม่เคยใช้เทรนโมเดลทั้งคู่):

| ตัวชี้วัด | h5 เดิม (production) | h5_v2 (ใหม่) | เปลี่ยนแปลง |
|---|---:|---:|---:|
| MAE (m³/day) | 46,779 | 7,886 | **-83%** |
| Median AE | 29,206 | 2,374 | **-92%** |
| Bias (ทำนายสูง/ต่ำกว่าจริงเฉลี่ย) | +45,466 | -103 | **แทบเป็นศูนย์** |
| NSE | -36.73 | -0.54 | ดีขึ้นมาก (ยังติดลบ) |

ช่วงพลาโต 85,000–136,000 ที่ค้างอยู่เกือบ 3 สัปดาห์ในโมเดลเดิม **หายไปหมด** ในโมเดลใหม่ — h5_v2 ทำนายใกล้ 0 ในวันที่ actual เป็น 0 จริง และทำนายสมเหตุสมผลมากขึ้นในวันฝนตก

**หมายเหตุ:** NSE ยังติดลบอยู่ (-0.54) หมายความว่าโมเดลยังไม่ดีกว่าการทำนายด้วยค่าเฉลี่ยธรรมดา — ไม่ใช่โมเดลที่ "ดี" ในความหมายทั่วไป แต่ **บั๊กร้ายแรงที่ทำให้เกิดค่าทำนายสุดขั้วผิดปกติถูกกำจัดแล้ว** ซึ่งเป็นเป้าหมายหลักของงานนี้

ไฟล์โมเดลใหม่: `h5_v2_final_fulldata.pkl` / `.cbm` (อยู่ในโฟลเดอร์ experiments เท่านั้น)

## 3. ส่วนที่ 2: Post-hoc Bias Recalibration (ทุก horizon)

### 3.1 วิธีการ

ใช้ `forecast_accuracy_log.csv` (329 แถวที่มี actual ครบ) แบ่งแบบ chronological ต่อ horizon: 65% แรก (fit) ใช้คำนวณ bias คงที่ (`mean(predicted - actual)`), 35% หลัง (holdout) ใช้ประเมินผลแบบ honest out-of-sample (ไม่เคยเห็นตอน fit) — horizon 5 ใช้ค่าจาก h5_v2 เป็น base แทนของเดิม

สูตรแก้: `corrected = max(raw_prediction - bias_correction, 0)`

### 3.2 ผลลัพธ์ต่อ horizon (วัดบน holdout เท่านั้น)

| Horizon | n (fit/holdout) | bias correction | MAE ก่อน | MAE หลัง | ผล |
|---|---|---:|---:|---:|---|
| h1 | 32/18 | +919 | 9,344 | 8,914 | ดีขึ้นเล็กน้อย |
| h2 | 31/18 | -225 | 4,293 | 4,443 | **แย่ลงเล็กน้อย — ไม่แนะนำใช้** |
| h3 | 31/17 | +8,728 | 9,220 | 6,172 | ดีขึ้นชัดเจน (-33%) |
| h4 | 30/17 | +11,781 | 10,573 | 6,280 | ดีขึ้นชัดเจน (-41%) |
| h5 (ใช้ h5_v2 เป็น base) | 29/17 | -801 | 5,131 | 5,790 | แย่ลง — **ไม่ต้องใช้ซ้ำ เพราะ h5_v2 แก้ bias ไปแล้ว** |
| h6 | 29/16 | +7,425 | 12,836 | 8,101 | ดีขึ้นชัดเจน (-37%) |
| h7 | 28/16 | +23,195 | 21,111 | 8,934 | ดีขึ้นมาก (-58%) |

**MAE เฉลี่ยถ่วงน้ำหนักทุก horizon: 10,188 → 6,917 (-32%)**

### 3.3 คำแนะนำการใช้งาน

- **ใช้ bias correction กับ h1, h3, h4, h6, h7** — ช่วยลด error ได้จริงและสม่ำเสมอ (h3/h4/h6/h7 คือ horizon ที่มี systematic over-prediction ชัดเจนตามรายงานก่อนหน้า)
- **ไม่ใช้กับ h2** — bias เดิมใกล้ศูนย์อยู่แล้ว การแก้เพิ่มมีแต่เพิ่ม noise
- **ไม่ใช้กับ h5** — ใช้ h5_v2 (โมเดลใหม่) แทน เพราะแก้ที่ต้นตอโดยตรงและได้ผลดีกว่า
- ค่า bias คำนวณจากแค่ 28-32 แถว (fit) — **ควร refit ใหม่เป็นระยะ** (เช่นทุกเดือน) เมื่อ log สะสมมากขึ้น เพื่อลด noise ของค่าคงที่นี้

ไฟล์ผลลัพธ์: `bias_recalibration_holdout_results.csv`, `bias_correction_config_PROPOSED.json`

## 4. ข้อจำกัดที่ควรทราบ

1. **Sample size เล็ก** — log มีแค่ ~44-50 แถวต่อ horizon, holdout เหลือ 16-18 แถว ตัวเลขข้างต้นมี noise พอสมควร ควรตรวจซ้ำเมื่อข้อมูลสะสมมากขึ้น (คาดว่า Water Demand live ใช้เวลาราว 3 สัปดาห์ตามที่เคยประเมินไว้ — Reservoir Inflow log ก็ควรสะสมต่อเนื่องเช่นกัน)
2. **h5_v2 ยังไม่ใช่โมเดลที่ "ดี"** — เพียงแก้บั๊ก extreme-value ที่ทำให้เกิด error มหาศาล ไม่ใช่การปรับปรุงความแม่นยำพื้นฐานของ horizon 5 (ซึ่งเป็นเรื่องยากเพราะข้อมูล zero-inflated ตามรายงานก่อนหน้า)
3. **โมเดลอื่น (h6, h7) ก็มีอาการคล้ายกันแฝงอยู่ได้** — แม้ยังไม่เห็นอาการ "plateau" รุนแรงแบบ h5 แต่ทั้งคู่ก็มี tree_count สูงใกล้เพดาน (183, 252 จาก 300) และ NSE ติดลบเช่นกัน แนะนำให้ตรวจสอบเชิงลึกแบบเดียวกันในรอบถัดไปหากมีเวลา (ไม่ได้ทำในรอบนี้เพราะ user ระบุเฉพาะ h5)
4. **ยังไม่ deploy** — ทุกอย่างอยู่ใน `01_data/experiments/inflow_h5_bias_fix_20260907/` ตามที่สั่งไว้ ("ไม่แตะ production") รอคำสั่ง "final" ก่อนจะย้ายไป deploy จริง

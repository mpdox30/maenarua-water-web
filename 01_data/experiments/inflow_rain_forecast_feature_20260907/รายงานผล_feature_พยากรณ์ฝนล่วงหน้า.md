# รายงานผล: เพิ่ม Feature พยากรณ์ฝนล่วงหน้า (ข้อ 4)

**วันที่:** 2026-09-07
**ขอบเขต:** ทำแยกจากงาน h5/bias recalibration ทั้งหมด (`01_data/experiments/inflow_rain_forecast_feature_20260907/`) — ไม่แตะ production

---

## สรุปสั้น: **ผลลัพธ์ไม่เป็นไปตามคาด — ไม่แนะนำให้ deploy feature นี้ในรูปแบบปัจจุบัน**

ทดสอบผ่าน 2 วิธี ได้ผลตรงข้ามกัน:

| วิธีทดสอบ | ผล |
|---|---|
| Walk-forward CV (ภายในชุดเทรนเดิม) | **ดีขึ้นชัดเจนทุก horizon** (h5 ดีขึ้นสุด +0.79 NSE) |
| Backtest จริงบนข้อมูล ส.ค.-ก.ย. 2026 (นอกช่วงเทรน) | **แย่ลงเกือบทุก horizon** บางตัวแย่ลงรุนแรงมาก (h6, h7) |

**สาเหตุ**: feature ใหม่ (ผลรวมฝนพยากรณ์ล่วงหน้า) มีช่วงข้อมูลย้อนหลังแค่ ~14 เดือน (archive เริ่ม มิ.ย. 2025) เมื่อนำไปทำนายช่วงฤดูฝนจริง (ส.ค.-ก.ย. 2026) ค่า feature ใหม่หลายวัน **เกินขอบเขตที่โมเดลเคยเห็นตอนเทรน** โมเดล tree-based (CatBoost) ทายค่านอกขอบเขตไม่ได้ (extrapolation) จึง "ค้าง" ที่ค่าสุดขั้วซ้ำๆ — **อาการเดียวกับบั๊ก h5 เดิมที่เพิ่งแก้ไป แต่คราวนี้เกิดจาก feature ตัวใหม่แทน**

ตัวอย่างชัดเจน: h5 ช่วง 2-7 ส.ค. 2026 ทายค่าซ้ำเกือบเป๊ะที่ ~178,600–187,600 ลบ.ม./วัน ติดต่อกันหลายวัน (เหมือน plateau เดิมของบั๊ก h5)

## ผลพลอยได้ที่สำคัญ (แม้ feature หลักจะไม่เวิร์ก)

**การใช้ early stopping + regularization แบบเดียวกับที่แก้ h5 ไปแล้ว ถ้าใช้กับทุก horizon (ไม่ใช่แค่ h5) ช่วยลด MAE ได้มากในเกือบทุก horizon แม้ไม่เพิ่ม feature ใหม่เลย:**

- h1: 7,373 → 6,797
- h2: 5,769 → 4,320
- h3: 12,371 → 8,419
- h4: 13,490 → 9,291
- h5: 46,108 → 9,488 (ตรงกับที่รายงานไปแล้วในงานก่อนหน้า)
- h6: 14,190 → 15,398 (แย่ลงเล็กน้อย)
- h7: 24,853 → 20,984

นี่คือ **win แยกต่างหากที่ควรนำไปใช้ต่อ** — regularization ทั่วทั้ง 7 โมเดล (ไม่ใช่แค่ h5) เป็นการปรับปรุงที่มีหลักฐานหนักแน่นกว่า feature พยากรณ์ฝนมาก และไม่ต้องพึ่งข้อมูลภายนอกเพิ่ม

## ข้อเสนอแนะ (รอบแรก — ก่อนปรับ feature engineering)

1. ~~ไม่แนะนำ deploy feature พยากรณ์ฝนล่วงหน้าในรูปแบบปัจจุบัน (raw cumulative forecast rain)~~ → **ปรับแล้ว ดูส่วนที่ 2 ด้านล่าง**
2. **แนะนำ deploy การ regularize ทั้ง 7 horizon** (early stopping แบบเดียวกับ h5_v2) — ได้ผลดีกว่ามาก วัดจากข้อมูลจริง โดยไม่ต้องพึ่ง external API เลย (ยืนยันอีกครั้งในส่วนที่ 2)

## ส่วนที่ 2: ปรับวิธี engineer feature ใหม่ (ทำตามคำขอ "ลองปรับวิธี engineer feature ฝนใหม่ก่อน")

ทดสอบ 4 วิธีแปลง `Rain_fcst_cum_h{N}` (ผลรวมฝนพยากรณ์ล่วงหน้า) ให้ "extrapolate ปลอดภัยขึ้น": clip ที่ p90, clip ที่ p99, binary (เกิน median หรือไม่), quartile bin (4 กลุ่ม) — เทียบกับ baseline (ไม่มี feature ใหม่, regularized)

### รอบแรก (เลือก threshold โดยดู MAE บน log ทั้งชุด — เสี่ยง overfit เข้ากับ holdout)

| Horizon | Base (ไม่มี feature) | clip_p90 | clip_p99 | binary_median | quartile_bin |
|---|---:|---:|---:|---:|---:|
| h1 | 6,797 | 6,844 | 7,076 | 6,844 | 6,845 |
| h2 | 4,320 | 4,444 | 4,327 | 4,620 | 4,491 |
| h3 | 8,419 | 9,609 | 8,911 | **7,942** | 8,609 |
| h4 | 9,291 | 9,784 | 9,210 | **7,913** | **7,886** |
| h5 | 9,488 | 11,357 | 11,251 | 9,999 | 10,731 |
| h6 | 15,398 | 15,244 | 39,811 | **14,298** | **14,481** |
| h7 | 20,984 | 27,543 | 51,319 | 23,533 | 22,883 |

→ **binary (เกิน threshold หรือไม่) เป็นวิธีที่ extrapolate ปลอดภัยที่สุด** ดีกว่า continuous-clipped เสมอ — สมเหตุสมผลเพราะ binary ไม่มีทาง "ค้างที่ค่าสุดขั้ว" ได้อีก (ค่าเป็นได้แค่ 0 หรือ 1)

### รอบสอง (honest split: เลือก threshold จาก log 65% แรกตามเวลา, วัดผลบน 35% หลังที่ไม่เคยใช้เลือก threshold)

เพื่อไม่ให้ตัวเลขดีเกินจริงจากการ "เลือก threshold ที่เข้ากับ holdout พอดี" ทำ sweep threshold (30th-80th percentile ของชุดเทรน) แล้วแบ่ง log เป็น fit 65% (เลือก threshold) / holdout 35% (วัดผลจริง ไม่เคยเห็นตอนเลือก):

| Horizon | n (fit/holdout) | Threshold ที่เลือก | MAE holdout (ไม่มี feature) | MAE holdout (มี binary feature) | ผล |
|---|---|---|---:|---:|---|
| h1 | 32/18 | p50 (1.9mm) | 8,703 | 8,941 | แย่ลง |
| h2 | 31/18 | p80 (17.8mm) | 3,645 | 3,979 | แย่ลง |
| h3 | 31/17 | p80 (27.3mm) | 8,587 | **7,303** | **ดีขึ้น 15%** |
| h4 | 30/17 | p50 (14.4mm) | 7,155 | 7,348 | แย่ลง (เล็กน้อย) |
| h5 | 29/17 | p40 (8.5mm) | 7,071 | 7,744 | แย่ลง |
| h6 | 29/16 | p30 (3.1mm) | 14,803 | **12,928** | **ดีขึ้น 13%** |
| h7 | 28/16 | p80 (61.0mm) | 18,501 | **17,965** | ดีขึ้นเล็กน้อย (3%) |

**นี่คือผลลัพธ์ที่เชื่อถือได้ที่สุด** (threshold ไม่เคยเห็น holdout ตอนเลือก) — สรุป: **feature พยากรณ์ฝนแบบ binary ช่วยได้จริงเฉพาะ h3, h6, h7** (horizon กลาง-ยาวที่โมเดลเดิมแม่นน้อยสุดอยู่แล้ว) ส่วน h1, h2, h4, h5 ไม่ควรใส่ feature นี้ (ทำให้แย่ลงเล็กน้อยถึงปานกลาง)

หมายเหตุ: ตัวอย่าง holdout มีแค่ 16-18 แถวต่อ horizon ตัวเลขยังมี noise พอสมควร ควรตรวจซ้ำเมื่อ log สะสมมากขึ้น

### ข้อเสนอแนะสุดท้าย (รวมทั้ง 2 ส่วน)

1. **ใช้ regularization (early-stopping) กับทุก horizon เป็นฐาน** — ยืนยันซ้ำว่าเป็นการปรับปรุงที่มีหลักฐานหนักแน่นที่สุด ควรทำก่อนอื่น
2. **เพิ่ม binary rain-forecast feature เฉพาะ h3, h6, h7** โดยใช้ threshold ที่ tune ไว้ (27.3mm/3วัน, 3.1mm/6วัน, 61.0mm/7วัน ตามลำดับ) — อย่าใส่ h1, h2, h4, h5
3. **เรื่อง bias recalibration ที่จะทำต่อ**: ควร fit บนผลลัพธ์ของโมเดลชุดสุดท้ายนี้ (regularized ทุก horizon + binary rain feature เฉพาะ h3/h6/h7) ไม่ใช่ base เปล่าๆ หรือ raw-continuous-feature ที่พิสูจน์แล้วว่าแย่กว่า
4. ถ้าจะขยายผลต่อในอนาคต: สะสม archive ให้ยาวกว่า 14 เดือน (ครอบคลุมหลายปีฤดูฝน-แล้ง) น่าจะทำให้ threshold ที่เลือกไว้เสถียรขึ้นและอาจขยายไปช่วย h1/h2/h4/h5 ได้ด้วย

# ผลทดลอง feature ข้อ 1 (is_release_active) + ข้อ 2 (daily_max/range_level_24h) รอบใหม่ (2026-09-07)

สถานะ: **ทดสอบเสร็จแล้วในโฟลเดอร์นี้เท่านั้น ไม่ได้แตะ production ที่รันอยู่**

## สรุปสั้น: ยังไม่แนะนำให้ deploy ทั้งคู่ ด้วยเหตุผลคนละแบบ

| feature | ผลรอบนี้ | เทียบกับผลเดิม (31 ก.ค.) |
|---|---|---|
| is_release_active | **ยังทดสอบไม่ได้จริง — พิสูจน์แล้วว่าไม่มีทางเป็นอื่น** | สรุปเดิมยังใช้ได้ ยืนยันซ้ำด้วยวิธีที่เข้มกว่า |
| daily_max/range_level_24h | ผลผสม ไม่ชัดเจนบน CV + **validate กับ log จริงไม่ได้เลยตอนนี้** | ทิศทางคล้ายเดิม (ผสม) แต่ยังขาดขั้นตอนสำคัญ |

## 1. is_release_active — ทำไมยังทดสอบไม่ได้

ใช้วิธี honest holdout (แบ่งข้อมูล 80% แรกตามเวลาไว้ train, 20% ท้ายสุดเก็บไว้เป็น holdout ที่ไม่แตะเลย
จนกว่าจะวัดผล — วิธีเดียวกับที่ใช้ tune bias correction/threshold รอบก่อน) พบว่า:

- ช่วง train (80% แรก = ถึง 2026-05-06) มี is_release_active **เป็น 0 ทุกแถว ไม่มีค่า 1 เลยแม้แต่แถวเดียว**
- ช่วง holdout (20% หลัง = 2026-05-06 ถึง 2026-07-23) มีทั้ง 0 และ 1 (28 จาก 79 แถว)

โมเดลไม่มีทางเรียนรู้อะไรจาก feature นี้ได้เลย เพราะไม่เคยเห็นค่า 1 ตอน train — ผลคือ prediction
เหมือนกับ baseline **เป๊ะทุกตัวเลข** (ยืนยันในไฟล์ `honest_holdout_results.csv`)

สาเหตุคือข้อมูลปล่อยน้ำที่มีอยู่ตอนนี้เป็น **event เดียว ต่อเนื่องไม่ขาดช่วง** (26 มิ.ย. 2026 ถึง
14 ต.ค. 2026 ตาม `release_events.csv` ล่าสุด — ยังไม่ปิด) ซึ่งอยู่ท้ายสุดของช่วงข้อมูล training พอดี
ไม่ว่าจะขยับจุดตัด train/test ตรงไหนตามลำดับเวลา ก็จะได้แค่ "train ไม่เห็นเลย" หรือ "test ไม่มี contrast"
อย่างใดอย่างหนึ่งเสมอ — **เป็นข้อจำกัดเชิงโครงสร้างของข้อมูล ไม่ใช่เรื่องโมเดลหรือวิธี tune**

ที่แย่ไปกว่านั้นสำหรับการ validate กับข้อมูลจริง: ช่วงเวลาทั้งหมดของ `forecast_accuracy_log.csv`
(27 มิ.ย. – 6 ก.ย. 2026, 52 วัน) **อยู่ในช่วง event ปล่อยน้ำที่ยังเปิดอยู่ตลอดทั้งหมด** — feature นี้จะ
เป็นค่าคงที่ 1.0 ทุกวันถ้าเอาไปทดสอบกับ log จริงตอนนี้ วัดผลอะไรไม่ได้เลยแม้จะมีข้อมูลเพิ่มจากเดือน
ก.ค.-ก.ย. แล้วก็ตาม

**คำแนะนำ**: เหมือนเดิม — เก็บ feature นี้ไว้ก่อน ยังไม่ deploy เพราะพิสูจน์ประโยชน์ไม่ได้ (ไม่ใช่พิสูจน์ว่า
ไม่มีประโยชน์) รอจนกว่า event ปล่อยน้ำจะปิดจริงหรือมี event ใหม่เปิด/ปิดสลับ ถึงจะมี contrast ให้ทดสอบได้

## 2. daily_max_level_24h / daily_range_24h

### วิธีทดสอบ
Honest holdout เดียวกับข้างบน (80/20 ตามเวลา, ไม่ใช้ walk-forward CV แบบเดิม) + hyperparameter
regularized (early-stopped) ชุดที่ deploy จริงตอนนี้ — ต่างจากรอบ 31 ก.ค. ที่ใช้ hyperparameter เดิม
(ไม่ regularize) และ walk-forward CV หลาย fold

### ผล (NSE บน holdout, เทียบ baseline = feature set ที่ deploy จริงตอนนี้ต่อ horizon)

| H | baseline | +range | diff |
|---|---|---|---|
| 1 | 0.905 | 0.911 | +0.006 |
| 2 | 0.761 | 0.765 | +0.004 |
| 3 | 0.548 | 0.511 | -0.037 |
| 4 | 0.419 | 0.387 | -0.032 |
| 5 | 0.270 | 0.241 | -0.029 |
| 6 | 0.128 | 0.121 | -0.007 |
| 7 | -0.004 | 0.006 | +0.010 |

**ผลยังผสมเหมือนรอบก่อน** — H1,H2,H7 ดีขึ้นเล็กน้อย, H3,H4,H5,H6 แย่ลง แม้จะเปลี่ยนทั้ง hyperparameter
(เป็นแบบ regularized) และวิธี split (honest holdout แทน walk-forward CV) ทิศทางโดยรวมก็ยังไม่ชี้ชัดว่า
ช่วยจริง โดยเฉพาะ **H3 ที่เป็นเป้าหมายหลัก (1 ใน 3 วันแรก) กลับแย่ลง (-0.037)**

### ข้อจำกัดสำคัญที่ต้องบอกตรงๆ: validate กับ log จริงไม่ได้เลยตอนนี้

ตัวเลข NSE ข้างบนมาจาก **training data เท่านั้น** (คล้าย walk-forward CV รอบก่อน) — ซึ่ง session นี้
เพิ่งพิสูจน์มาแล้วครั้งหนึ่งว่า **ผล CV บนข้อมูล training อาจหลอกได้** (feature พยากรณ์ฝนล่วงหน้าแบบ
continuous ก็ดูดีบน CV แต่พังจริงตอน backtest กับ log) วิธีที่น่าเชื่อถือกว่าคือ reconstruct feature
"ตามเวลาจริง" แล้วเทียบกับ prediction ที่ log ไว้จริงใน `forecast_accuracy_log.csv` (แบบที่ทำกับ
h5/rain-forecast feature ก่อนหน้านี้)

**แต่ทำแบบนั้นกับ feature นี้ไม่ได้ตอนนี้** เพราะ:
- ไฟล์ข้อมูลรายชั่วโมง `Raw Data_RES002 station.xlsx` ที่ใช้สร้าง feature นี้ข้อมูลจบแค่ **2026-06-27**
- ช่วงของ `forecast_accuracy_log.csv` คือ 2026-06-27 ถึง 2026-09-06 — **แทบไม่ overlap กันเลย**
- ระบบ telemetry สดที่มีอยู่จริง (`reservoir_telemetry_from_sheet.py` อ่านจาก Google Sheet
  "wide_log" ที่ผู้ใช้ตั้ง Apps Script poll ทุก 10 นาที) **ยังไม่ได้เชื่อมเข้า pipeline การพยากรณ์จริง
  (`data_pipeline.py`)** — ตอนนี้ใช้อยู่แค่ในระบบคู่ขนาน shadow-mode (`reservoir_daily_orchestration.py`)
  เท่านั้น ไม่ใช่แหล่งข้อมูลที่ CatBoost model ใช้จริง

พูดง่ายๆ คือ **ต่อให้ผล CV ออกมาดีชัดเจนกว่านี้ ก็ยังเอาไป deploy ตอนนี้ไม่ได้อยู่ดี** เพราะ production
ไม่มีทางคำนวณ feature นี้แบบสดๆ ทุกเช้าได้ (ไม่มีท่อข้อมูลรายชั่วโมงที่อัปเดตต่อเนื่อง)

### คำแนะนำ

ไม่แนะนำให้เดินหน้า deploy feature นี้ตอนนี้ ด้วย 2 เหตุผลรวมกัน (ผล CV ไม่ชัดเจน + ไม่มีทาง validate
กับ log จริงหรือรันสดใน production ได้เลย) ถ้าอยากเดินหน้าต่อจริงๆ ต้องทำ 2 อย่างนี้ก่อน (เป็นงานแยก
อีกรอบ ใหญ่กว่าที่ทำวันนี้):

1. **ขอไฟล์ wide_log ล่าสุดจากผู้ใช้** (export/publish-to-web CSV จาก Google Sheet ที่ Apps Script
   สะสมไว้ตั้งแต่กลาง ก.ค.) เพื่อขยาย coverage ของ max/range_24h ให้ครอบคลุมช่วง log จริงถึงปัจจุบัน
   แล้ว validate แบบ honest holdout กับ log จริงเหมือนที่ทำกับ h5/rain-forecast feature
2. **เชื่อม telemetry สดเข้า `data_pipeline.py` จริง** ถ้าอยากใช้ feature นี้ใน production แบบวันต่อวัน
   (ตอนนี้เชื่อมแค่ระบบ shadow-mode คู่ขนาน)

สถานะ: **เอกสารแผนเท่านั้น ยังไม่ได้ลงมือทำอะไร** ตามที่ขอ

## คำตอบตรงคำถาม

### 2. ต้องปรับ/ทำอะไรเพิ่มบ้าง

#### 2.1 พอร์ต 3 สคริปต์ที่เหลือ (งานทำได้แน่ๆ ไม่มีข้อจำกัดเชิงเทคนิค)

ใช้ pattern เดียวกับที่ทำสำเร็จมาแล้วตอน migrate `data_pipeline.py` → `data_pipeline_colab.py` (คัดลอก
+ แก้เฉพาะจุดที่พึ่ง Windows/ArcGIS):

- `reservoir_daily_orchestration.py` → ไม่มีอะไรเป็น Windows-only เลย (อ่าน Google Sheet ผ่าน HTTP,
  เขียน xlsx ด้วย openpyxl, git push) — พอร์ตตรงไปตรงมา
- `monitoring_data_builder.py` → เช่นเดียวกัน ไม่มี Windows-only dependency
- `sar_background_job.py` → ใช้ GEE service account เหมือน `chirps_feature.py`/`sar_classification.py`
  ที่ port สำเร็จไปแล้ว ใช้ credential เดิม (Colab Secret `GEE_SA_KEY_JSON`) ได้เลย

**ไม่มีตัวไหนติด ArcGIS/era5-grib แบบที่ `era5t_worker.py` เคยติด** (ปัญหานั้นแก้ไปแล้วตอน migrate
`data_pipeline.py` ด้วย `era5t_worker_colab.py`)

#### 2.2 ปัญหาใหญ่กว่า: Colab เองไม่มีระบบ "รันตามเวลาแบบไม่ต้องเปิดเอง" ที่เชื่อถือได้

**ย้อนความ**: ตอนตัดสินใจ migrate ครั้งแรก (19 ก.ค. 2026, ดู `COLAB_MIGRATION_PLAN.md` หัวข้อ 1)
คุณเคยตรวจสอบและสรุปว่า **Colab Pro/Pro+ ปกติไม่มีฟีเจอร์รันตามเวลาอัตโนมัติเลย** (มีแต่ใน Colab
Enterprise ซึ่งต้องผูก GCP billing แยก) จึงตัดสินใจเปิด Colab เองทุกวันแทน

**อัปเดตตอนนี้ (ก.ย. 2026)**: ค้นเพิ่มพบว่า **Colab Pro ตอนนี้มีปุ่ม "Schedule" สำหรับ notebook บน
Drive แล้ว** (ต่างจากตอน ก.ค. — น่าจะเป็นฟีเจอร์ใหม่ที่เพิ่งออก) แต่มีข้อจำกัดสำคัญที่ต้องรู้ก่อนพึ่งพา:

- **รองรับความถี่แค่ระดับ "วันละครั้ง" เป็นอย่างเร็วที่สุด** ไม่มีโหมดรันถี่กว่านั้น (นาที/ชั่วโมง) —
  **แปลว่าต่อให้ใช้ฟีเจอร์นี้ ก็ยังพา `monitoring_data_builder.py` (ทุก 15 นาที) ไปวางบน Colab
  scheduler ไม่ได้อยู่ดี** ต้องหาทางอื่นให้ตัวนี้โดยเฉพาะ
- เจอรายงานปัญหาจริง (GitHub issue ของทีม Colab) ว่า schedule มีโอกาส **หยุดทำงานเองหลังผ่านไป
  ~2 วัน ต้องตั้งใหม่มือ** — ยังไม่นิ่งพอจะเชื่อ 100% สำหรับงานที่อยากให้ "ไม่ต้องแตะเลย"
- ยังไม่ได้ทดสอบจริงกับ notebook นี้โดยเฉพาะ (ที่ต้องใช้ Secrets หลายตัว + รันหลายนาที) — ควรทดลองก่อน
  เชื่อถือ ไม่ควรผูกทั้งระบบกับฟีเจอร์นี้ทันทีโดยไม่มีแผนสำรอง

#### 2.3 ทางเลือกสำหรับ "trigger อัตโนมัติ" — เทียบ 3 ทาง

| ทาง | ใช้ได้กับ | ความถี่ต่ำสุด | ความน่าเชื่อถือ | ต้องทำเพิ่ม |
|---|---|---|---|---|
| **A. Colab Pro Schedule button** | pipeline หลัก + orchestration + SAR (วันละ/สัปดาห์ละครั้ง) | ~1 วัน | ปานกลาง (มีรายงานบั๊กหยุดเองหลัง ~2 วัน) | ตั้ง schedule ในแต่ละ notebook, ต้องคอยเช็คว่ายังรันอยู่ |
| **B. GitHub Actions (cron)** | **ทั้ง 4 งาน ได้หมดรวม 15 นาที** | ไม่จำกัด (ตั้งได้ถึงระดับนาที) | สูง (ระบบ cron ของ GitHub เองที่ใช้กันแพร่หลายทั่วโลก ไม่ใช่ฟีเจอร์เสริมที่เพิ่งออก) | เขียน workflow YAML (ใหม่, ไม่เคยทำในโปรเจกต์นี้), ย้าย credential จาก Colab Secrets → GitHub Actions Secrets |
| **C. คงเปิดมือทุกวัน (ปัจจุบัน)** | ทุกงาน | - | สูงสุด (คนคุมเอง) | ไม่ต้องทำอะไรเพิ่ม แต่ไม่ตอบโจทย์ "ไม่ต้องเปิดโน๊ตบุ๊ค" |

**ข้อสังเกตสำคัญ**: ทุกสคริปต์ในระบบนี้ (orchestration, monitoring, SAR, pipeline หลัก) **ไม่มีตัวไหน
ต้องใช้ GPU เลย** (GEE ประมวลผลฝั่งเซิร์ฟเวอร์ Google เอง, CatBoost/LightGBM inference เบามาก,
ERA5T แค่ดึงไฟล์) เหตุผลที่ใช้ Colab แต่แรกคือ "เลี่ยงปัญหา cdsapi/cfgrib ติดตั้งไม่ได้บน Windows"
ไม่ใช่เพราะต้องการ compute พิเศษของ Colab — **ทาง B (GitHub Actions) ทำงานเดียวกันได้ครบทุกอย่าง
บน Linux runner ฟรีของ GitHub เอง โดยไม่ต้องพึ่ง Colab เลยแม้แต่ตัวเดียว** (runner ก็เป็น Linux
เหมือนกัน ติดตั้ง cdsapi/cfgrib ได้แบบเดียวกับที่ทำสำเร็จบน Colab แล้ว)

## แผนที่แนะนำ (3 ตัวเลือก เรียงตามความอัตโนมัติ)

### แผน 1 — "เต็มรูปแบบ Colab" ตามที่ถามมา
1. Port `reservoir_daily_orchestration.py`, `monitoring_data_builder.py`, `sar_background_job.py` → `_colab.py`
2. ตั้ง Colab Pro Schedule ให้ pipeline หลัก + orchestration (วันละครั้ง) และ SAR (สัปดาห์ละครั้ง)
3. **`monitoring_data_builder.py` (15 นาที) ยังต้องมีทางแยกต่างหาก** — ตัวเลือกย่อย:
   - (ก) ลดความถี่เหลือวันละครั้ง (พร้อมกับ pipeline หลัก) — ยอมรับว่าการ์ด %ความจุ/monitoring.html
     จะไม่สดระหว่างวัน (จาก near-real-time เป็นอัปเดตวันละครั้ง)
   - (ข) ย้ายเฉพาะตัวนี้ไป GitHub Actions (ที่เหลือยังอยู่ Colab) — ผสมทาง B บางส่วน
   - (ค) ปล่อยไว้บน Windows Task Scheduler ต่อไป (ยังต้องเปิดเครื่อง Windows ไว้ แต่แค่เพื่องานเดียวนี้)
4. ความเสี่ยง: ต้องคอยเช็คว่า Colab schedule ยังทำงานอยู่ (บั๊กหยุดเองที่เจอรายงานไว้)

### แผน 2 — "เต็มรูปแบบ GitHub Actions" (แนะนำถ้าเป้าหมายจริงคือ "ไม่ต้องแตะอะไรเลย")
1. Port 3 สคริปต์เหมือนแผน 1 แต่เป้าหมายคือรันบน GitHub Actions runner ไม่ใช่ Colab
2. ย้าย credential ทั้งหมด (CDS API, GEE service account, GitHub PAT ไม่จำเป็นแล้วเพราะรันในนั้นเลย)
   เข้า GitHub Actions Secrets
3. เขียน workflow YAML 4 ไฟล์ (แต่ละงาน 1 cron schedule ตรงตามที่ต้องการ รวม 15 นาทีได้จริง)
4. เลิกพึ่ง Google Drive mount/`sync_to_drive.bat` ไปเลย (Actions clone repo สดทุกรอบ ไม่ต้องมี
   ขั้น mirror-to-Drive อีกต่อไป — ตัดปัญหา "ลืม sync" ที่เจอมาตลอด session นี้ทิ้งไปด้วย)
5. ปิด Windows Task Scheduler ทั้งหมดได้จริง หลังเทียบผลคู่ขนานสัก 1-2 สัปดาห์ (เหมือน cutover
   plan เดิมที่วางไว้)
6. งานใหม่ทั้งหมด: เขียน YAML (ไม่เคยทำในโปรเจกต์นี้มาก่อน แต่เป็น pattern มาตรฐาน) + ทดสอบ

### แผน 3 — ผสม (ทำน้อยที่สุดตอนนี้ ขยายทีหลังได้)
1. Port แค่ `reservoir_daily_orchestration.py` ไป Colab ก่อน (ผูกกับ pipeline หลักที่มีอยู่แล้ว รันใน
   session เดียวกันทุกเช้าที่เปิด)
2. `monitoring_data_builder.py` + `sar_background_job.py` ปล่อยไว้บน Windows Task Scheduler เหมือนเดิม
   (ยังต้องเปิดเครื่อง Windows แต่แค่พอให้ 2 task นี้รันได้ ไม่ต้องเปิด "ทำงาน" อะไรเพิ่ม)
3. ทดลอง Colab Pro Schedule button กับ pipeline หลักดูก่อนว่าเสถียรจริงไหม (เสี่ยงต่ำ ทดสอบง่าย)
4. ตัดสินใจแผน 1 หรือ 2 อีกทีหลังเห็นผลทดลองจริง

## คำแนะนำของผม

ถ้าเป้าหมายจริงคือ **"ไม่ต้องเปิดโน๊ตบุ๊คเลย"** (ไม่ใช่แค่ "ไม่ต้องเปิดค้างไว้") — **แผน 2
(GitHub Actions) ตอบโจทย์ตรงกว่าแผน 1** เพราะ:
- แก้ปัญหา 15 นาทีได้จริง (ต่างจากแผน 1 ที่ยังต้องหาทางแยก)
- cron ของ GitHub เชื่อถือได้มากกว่า feature ใหม่ที่ยังมีรายงานบั๊ก
- เลิกพึ่ง Drive mount/sync_to_drive.bat ได้ ตัดปัญหา "ลืม sync" ที่เกิดขึ้นจริงมาแล้วรอบหนึ่งใน session นี้
- งานที่ต้องทำเพิ่ม (เขียน YAML) ไม่ได้ยากกว่าการตั้ง Colab Secrets ที่ทำมาแล้ว แค่เป็นของใหม่ที่ต้องเรียน

แต่แผน 2 ก็มีต้นทุน "เรียนรู้เครื่องมือใหม่" ที่แผน 1 ไม่มี (Colab เป็นสภาพแวดล้อมที่คุ้นแล้ว) — ถ้าอยาก
ทำน้อยที่สุดตอนนี้และไม่รีบ **แผน 3 เป็นจุดเริ่มที่สมเหตุสมผลที่สุด** เพราะเสี่ยงต่ำ ทดสอบ Colab
Schedule จริงก่อนตัดสินใจทุ่มไปทางไหนเต็มตัว

## สิ่งที่ยังไม่ได้ตรวจสอบ (ควรทำก่อนเริ่มลงมือจริง ไม่ว่าจะเลือกแผนไหน)

- GitHub repo เป็น private หรือ public — ถ้า private, GitHub Actions ฟรีมี quota 2,000
  นาที/เดือน (ยังไม่ได้เช็ค repo นี้ตั้งไว้แบบไหน) ถ้า public ไม่จำกัด

  หลายตัว + รันนานหลายนาทีได้ราบรื่นแค่ไหน (ข้อมูลที่หาได้เป็นแค่เอกสาร/รายงานทั่วไป ไม่ใช่ของ notebook นี้)
